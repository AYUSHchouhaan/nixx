Overview

The Nixx coding agent runs inside agent-brain (a LangGraph server) but never touches the filesystem or shell directly. All file, shell, and git operations are executed by a separate process, sandbox-worker, against an isolated cloned repo.

The two processes communicate exclusively through two BullMQ queues backed by Redis. This document explains the machinery that makes a single request/responses round-trip work — specifically the pair of files src/pending-calls.ts and src/result-consumer.ts in apps/agent-brain — and exactly where they are used.

The Problem

BullMqSandboxClient.call() must return a Promise that the agent can await. But the answer is not produced in that function. It is produced later, in a different process, and it arrives back in a different file (result-consumer.ts) on a different queue (sandbox-to-agent).

The core problem:

  • call() creates a Promise (file A, outbound queue).
  • result-consumer receives the answer (file C, inbound queue).
  • Two files, two queues, two processes — but only one Promise that must resolve.

The connection is a random commandId. File A registers the Promise under that id. File C looks it up when the answer arrives and resolves it. The registry that stores this mapping lives in pending-calls.ts.

Mental Model

Think of a restaurant:

  • You (the agent) hand the waiter (bullmq-sandbox-client) a numbered ticket (commandId) and wait at your table.
  • The kitchen (sandbox-worker) prepares the order in another room.
  • When ready, the kitchen calls out the ticket number to the front desk.
  • The front desk (result-consumer) looks up who holds that ticket (pending-calls.ts) and calls you up — resolving your Promise.

Where Each File Is Used

The only files that ever touch pending-calls.ts are bullmq-sandbox-client.ts (the writer) and result-consumer.ts (the reader). The only place result-consumer.ts is started is src/graph.ts at boot.

Step-by-Step Walkthrough

Suppose the AI agent (running inside agent-brain) decides to read a file with the read tool.

1
The agent calls a tool

packages/agent/programmer/tools/read.ts → helpers.ts sandboxCall() → deps.sandboxClient.call({ threadId, conversationId, sandboxId, command: "read_file", args }). deps.sandboxClient is the BullMqSandboxClient created in graph.ts.

2
call() registers a pending Promise and enqueues
const commandId = randomUUID();              // e.g. "3f8a-…-9c21"
const message = { type: "command", commandId, ...input };

return new Promise((resolve, reject) => {
  const timer = setTimeout(
    () => rejectPendingCall(commandId, new Error("Sandbox timeout …")),
    CALL_TIMEOUT_MS,                              // 120 000 ms
  );
  registerPendingCall(commandId, { resolve, reject, timer }); // ← store promise
  void agentToSandboxQueue.add("command", message);           // ← send to Redis
});

Now pending-calls.ts holds: commandCalls = Map { "3f8a-…-9c21" → { resolve, reject, timer } }. The tool call is blocked, awaiting that Promise.

3
sandbox-worker does the work and replies

A separate process picks the job off agent-to-sandbox, runs executor.ts → readFiles(), and posts a result message back to sandbox-to-agent carrying the same commandId.

4
result-consumer resolves the Promise
// result-consumer.ts
resolvePendingCall(data.commandId, { output, exitCode, error });

In pending-calls.ts, resolve():

  • looks up "3f8a-…-9c21" → finds the Promise
  • map.delete(commandId) — one-shot, removes it
  • clearTimeout(timer) — cancels the 120s timer
  • call.resolve(result) — the Promise in step 2 resolves, and the agent’s read tool returns the file contents.

The commandId is the only thing that connects step 2 and step 4.

File Anatomy

apps/agent-brain/src/pending-calls.ts
type PendingCall<T> = {
  resolve: (value: T) => void;      // resolve the agent's awaiting Promise
  reject:  (reason: Error) => void; // reject it (timeout / failure)
  timer:   ReturnType<typeof setTimeout>; // 120s safety-net timer
};

const commandCalls   = new Map<string, PendingCall<SandboxCallResult>>();
const provisionCalls = new Map<string, PendingCall<SandboxProvisionResult>>();

// generic helpers — register / resolve / reject, all one-shot
function register(map, commandId, call) { map.set(commandId, call); }
function resolve(map, commandId, result) {
  const call = map.get(commandId);
  if (!call) return false;              // already answered / timed out
  map.delete(commandId);                // one-shot
  clearTimeout(call.timer);             // cancel safety net
  call.resolve(result);
  return true;
}
function reject(map, commandId, reason) { /* same, but call.reject */ }

// typed public API (writer side)         (reader side)
// registerPendingCall / resolvePendingCall / rejectPendingCall
// registerPendingProvision / resolvePendingProvision / rejectPendingProvision
apps/agent-brain/src/result-consumer.ts
export function startResultConsumer() {
  const worker = new Worker(QUEUE_NAMES.sandboxToAgent, async (job) => {
    const data = job.data;

    if (data.type === "provision_result") {
      resolvePendingProvision(data.commandId, {
        sandboxId, sandboxPath, cloned, error,
      });
      return;
    }

    // everything else is a command result
    resolvePendingCall(data.commandId, { output, exitCode, error });
  }, { connection: redisConnection });

  // Safety net: if BullMQ reports the job failed (worker crashed before replying),
  // reject the pending promise instead of letting it hang.
  worker.on("failed", (job, err) => {
    const data = job?.data;
    if (!data?.commandId) return;
    if (data.type === "provision_result") {
      rejectPendingProvision(data.commandId, err);
      return;
    }
    rejectPendingCall(data.commandId, err);
  });

  return worker;
}

Function Reference — Who Calls What

Function (pending-calls.ts)Called byWhen
registerPendingCall bullmq-sandbox-client.ts (call) Every command request, before enqueueing
resolvePendingCall result-consumer.ts A result message arrives on sandbox-to-agent
rejectPendingCall bullmq-sandbox-client.ts and result-consumer.ts 120s timeout, queue.add failure, or worker job failure
registerPendingProvision bullmq-sandbox-client.ts (provision) Every provisioning (clone) request
resolvePendingProvision result-consumer.ts A provision_result message arrives
rejectPendingProvision same as rejectPendingCall (provision variant) timeout / enqueue failure / worker failure

The provision* functions are the identical mechanism but for the clone-a-repo request (triggered by the graph’s prepare-sandbox node calling deps.sandboxClient.provision(...)) instead of a file/shell command.

Failures & Timeouts

There are three independent safety nets. Together they guarantee the agent never hangs forever.

ScenarioGuardResult
Worker crashes before replying (job marked failed) worker.on("failed") in result-consumer.ts reject pending promise immediately with the real error
Job disappears silently / never answers 120s setTimeout in bullmq-sandbox-client.ts reject with “Sandbox timeout”
Redis enqueue itself fails queue.add(...).catch(...) in the client reject immediately with the enqueue error
Note: resolve()/reject() return false when the id is no longer in the map (already answered or already timed out). This makes the guards idempotent — the first one to fire wins, the rest are harmless no-ops.

Why Is pending-calls.ts a Separate File?

  • The writer (bullmq-sandbox-client.ts) only knows how to create requests.
  • The reader (result-consumer.ts) only knows how to consume replies.
  • Both need access to the same in-memory Map, but importing each other would create a cycle.

So the map lives in its own module, and both import from it. It is not a cache or a database — purely in-memory, one-shot, and lost if the agent-brain process restarts (which is fine, because a restart also destroys the awaiting Promises).

When Does This Actually Run?

  1. sandbox-worker must be running (bun run src/main.ts) to receive agent-to-sandbox jobs.
  2. agent-brain must be running as the LangGraph server (langgraphjs dev) so graph.ts boots startResultConsumer().
  3. A user sends a message in the web UI → apps/web/app/api/threads/[threadId]/run/route.ts → apps/web/app/lib/agent-brain.ts (client.runs.create(...), LangGraph SDK over HTTP) → the graph runs → prepare-sandbox provisions, tools issue commands → every command flows through this round-trip.

Key Takeaways

  • pending-calls.ts is a shared in-memory registry mapping commandId → awaiting Promise. It is the bridge between the request (bullmq-sandbox-client.ts) and the reply (result-consumer.ts).
  • result-consumer.ts is a BullMQ Worker that watches sandbox-to-agent and resolves the matching Promise, plus a failed handler that rejects on worker crashes.
  • The two processes never share memory — the commandId is the only link.
  • Everything is one-shot and idempotent: the first resolve/reject wins.
  • These files are used only inside apps/agent-brain and are wired together in src/graph.ts.
