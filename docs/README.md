# Nixx — Agent ↔ Sandbox Architecture

This document is the implementation reference for the agent, sandbox, and queue wiring inside the Nixx Turborepo. It describes the current state of the system, the data flow, the package boundaries, and exactly what is deferred.

## 1. High-level architecture

Nixx runs a coding agent that executes work inside an isolated sandbox. The agent does **not** touch the filesystem or shell directly. Instead it communicates with the sandbox through two BullMQ queues backed by Redis.

```
┌─────────────────────┐        Queue A          ┌──────────────────────┐
│     agent-brain      │   agent-to-sandbox      │    sandbox-worker     │
│  (LangGraph + HTTP)  │ ───────────────────────▶│  (executor process)   │
│                      │                          │                       │
│  SandboxClient       │ ◀───────────────────────│  executes commands     │
│  (await result)      │   sandbox-to-agent       │  returns output        │
└─────────────────────┘        Queue B          └──────────────────────┘
         ▲
         │ HTTP POST /run
         │
┌─────────────────────┐
│        web           │
│  (Next.js backend)   │
│  auth + thread mgmt  │
└─────────────────────┘
```

The split is deliberate:

- **agent-brain** owns reasoning (the LangGraph), but is sandbox-agnostic.
- **sandbox-worker** owns execution, but is agent-agnostic.
- The only contract between them is the message shapes and queue names in `@repo/contracts`.

## 2. Packages and apps

| Package / App | Responsibility |
|---|---|
| `@repo/contracts` | Shared queue config, message types, `SandboxClient` interface |
| `@repo/agent` | LangGraph programmer graph and sandbox-backed tools |
| `@repo/db` | Drizzle schema (users, conversations, threads) |
| `apps/agent-brain` | HTTP server that invokes the graph and bridges to BullMQ |
| `apps/sandbox-worker` | BullMQ consumer that executes commands in the sandbox |
| `apps/web` | Next.js primary backend; auth, thread/conversation management, calls agent-brain |

## 3. Message contract

### `SandboxCommandMessage` (Queue A — agent → sandbox)

```ts
{
  type: "command",
  commandId: string,       // correlation id
  threadId: string,
  conversationId: string,
  sandboxId: string,
  command: SandboxCommandName,
  args: Record<string, unknown>,
}
```

### `SandboxResultMessage` (Queue B — sandbox → agent)

```ts
{
  type: "result",
  commandId: string,       // same id as the request
  threadId: string,
  conversationId: string,
  sandboxId: string,
  output: string,
  exitCode: number,
  error?: string,
}
```

`commandId` is generated by the agent's `SandboxClient` using `randomUUID()`. The agent stores a pending resolver keyed by that id; when the worker publishes the result, the resolver is invoked and the waiting graph node resumes.

## 4. Supported sandbox commands

The current implementation is intentionally **read-only plus shell execution**. File mutation tools are deferred.

| Command | Purpose |
|---|---|
| `read_file` | Read one or more files |
| `glob` | Find files by pattern |
| `grep` | Search file contents |
| `run_command` | Execute a shell command |

**Deferred:** `write_file`, `edit`, and any other modify tools. The sandbox worker will gain these later without changing the queue contract.

## 5. Sandbox client

Defined in `apps/agent-brain/src/bullmq-sandbox-client.ts`.

```ts
class BullMqSandboxClient implements SandboxClient {
  async call(input) {
    const commandId = randomUUID();
    await agentToSandboxQueue.add("command", { type: "command", commandId, ...input });
    return new Promise((resolve, reject) => {
      // registered in pending-calls registry
      // resolved by result-consumer when the matching result arrives
    });
  }
}
```

There is a hard timeout of `120_000ms`. If the sandbox does not respond in time, the promise rejects and the graph gets a tool error.

## 6. Result consumer

Defined in `apps/agent-brain/src/result-consumer.ts`.

It runs a BullMQ `Worker` on `sandbox-to-agent`. For each result job, it looks up the matching pending call by `commandId` and resolves it. Failed jobs reject the pending call with the worker error.

The pending-call registry is a simple `Map<string, PendingCall>` in `apps/agent-brain/src/pending-calls.ts`.

## 7. Agent graph

Defined in `packages/agent/programmer/graph.ts`.

The graph is created through a factory so every invocation can carry its own ids and sandbox client:

```ts
createProgrammerGraph({
  sandboxClient,
  threadId,
  conversationId,
  sandboxId,
});
```

Nodes:

- `generate-action` — binds sandbox tools to the model and produces the next action.
- `take-action` — executes the first tool call from the last AI message.
- `reasoning-thinking` — placeholder loop node.
- `end-conclusion` — summarizes the completed run.

Routing:

- `mark_task_complete` tool call → `end-conclusion`
- any other tool call → `take-action`
- plain text response → `end-conclusion`
- after `take-action` → back to `generate-action`

The tools (`read`, `glob`, `grep`, `run`) are thin wrappers that map to `SandboxClient.call`. They do not run local filesystem operations.

## 8. Sandbox worker

Defined in `apps/sandbox-worker/src/main.ts`.

It runs a BullMQ `Worker` on `agent-to-sandbox`. For each command it:

1. Calls `executeSandboxCommand(root, command, args)`.
2. Publishes a `SandboxResultMessage` to `sandbox-to-agent`.

The executor (`apps/sandbox-worker/src/executor.ts`) currently works on a local directory root (`SANDBOX_ROOT`, defaulting to `process.cwd()`). This is the integration point for a real sandbox backend later.

## 9. IDs, threads, and conversations

Thread and conversation IDs are owned by the main database (`@repo/db`), not by the agent.

### `conversations`

| Column | Type | Notes |
|---|---|---|
| `id` | text | PK, generated with `randomUUID()` |
| `user_id` | text | FK to `users` |
| `title` | text | optional |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

### `threads`

| Column | Type | Notes |
|---|---|---|
| `id` | text | PK, generated with `randomUUID()` |
| `conversation_id` | text | FK to `conversations` |
| `user_id` | text | FK to `users` |
| `sandbox_id` | text | optional |
| `metadata` | jsonb | optional |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

The primary backend creates these rows and passes the ids to agent-brain. Ownership is enforced on the run route by comparing `thread.userId` with the authenticated session user.

## 10. Web API

### `POST /api/conversations`

Creates a conversation for the authenticated user.

```json
{ "id": "conversation-uuid" }
```

### `POST /api/threads`

Creates a thread inside a conversation.

Request:

```json
{
  "conversationId": "conversation-uuid",
  "sandboxId": "optional-sandbox-id"
}
```

Response:

```json
{ "id": "thread-uuid" }
```

### `POST /api/threads/:threadId/run`

Runs the agent against the thread's sandbox.

Request:

```json
{
  "query": "Implement ...",
  "notes": "optional context"
}
```

Response:

```json
{ "summary": "..." }
```

The route:

1. Resolves the session.
2. Loads the thread and verifies ownership.
3. Uses `thread.sandboxId ?? threadId` as the sandbox id for now.
4. Calls `POST {AGENT_BRAIN_URL}/run` with the ids and query.

## 12. Running the system

```powershell
# install
bun install

# start Redis, then run these in separate terminals:

# 1. sandbox worker
bun run dev --filter=sandbox-worker

# 2. agent brain
bun run dev --filter=agent-brain

# 3. web (primary backend)
bun run dev --filter=web
```

## 13. What is deferred

The following are explicitly out of scope for the current implementation:

- Sandbox modify tools (`write_file`, `edit`)
- Checkpointer (graph state persistence)
- SSE / streaming agent events
- UI for agent output
- GitHub installation token wiring in the agent path
- Real sandbox provisioning (currently `sandboxId` falls back to `threadId`)

## 14. Typechecking

```powershell
bun run check-types
```
