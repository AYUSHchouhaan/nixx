Overview

This change ports the message rendering / streaming logic from the Open SWE agent into Nixx, without copying Open SWE's exact Tailwind / framer-motion components. The goal is to correctly render user messages, AI reasoning, tool calls, and tool results for Nixx's sandbox tools (grep, glob, read, run, create_file, edit, mark_task_complete).

The frontend keeps Nixx's existing CSS-module aesthetic. The agent behavior is unchanged — only how the streamed state is interpreted and displayed changes, plus a small state-model split.

What Was Wrong

Before this change, chat-client.tsx had a single MessageRow that did almost no interpretation:

  • human → a right-aligned text bubble (this part was fine).
  • ai → rendered only contentToText(content), so the model's tool calls were invisible. The reasoning text and the tool call were not separated.
  • tool → rendered the raw result as a <pre> blob with no tool name and no link back to the tool call that produced it.
The state carried a single messages list used for both display and LLM context. This made it impossible to keep the displayed transcript intact while independently trimming/filtering what the model sees.

The Pattern We Inherited

Open SWE separates concerns in two ways that Nixx now mirrors:

1. Two message lists in state

  • messages — the transcript shown to the client; never truncated.
  • internalMessages — the list actually passed to the LLM; may be trimmed or filtered.

2. Client-side extraction in the dispatcher

  1. Guard the message type (human / ai / tool).
  2. Extract tool_calls from the AI message.
  3. Join ToolMessage results to tool calls on tool_call_id.
  4. Treat the AI message's text content as reasoning.
  5. Dispatch actionable tools to a rich ActionStep, and unmatched tool messages to a standalone result.

apps/web/app/app/[id]/message-view.tsx (new)
"use client";

// Core rendering module. It is the Nixx-styled port of Open SWE's:
//   thread/messages/ai.tsx  +  gen-ui/action-step.tsx  +  thread/messages/tool-calls.tsx

export function MessageView({ message, messages }) {
  if (message.type === "human") {
    return <HumanMessageView message={message} />;
  }

  if (message.type === "tool") {
    // Suppress tool messages already rendered inside their AI action step.
    const consumed = messages.some(
      (m) => m.type === "ai" &&
        (m.tool_calls ?? []).some((tc) => tc.id === message.tool_call_id),
    );
    if (consumed) return null;
    return <ActionItem action={mapToolMessageToAction(message, messages)} />;
  }

  // AI message
  const reasoningText = contentToText(message.content);
  const toolCalls = message.tool_calls ?? [];

  if (toolCalls.length > 0) {
    const actions = toolCalls.map((toolCall) => {
      const toolMessage = messages.find(
        (m) => m.type === "tool" && m.tool_call_id === toolCall.id,
      );
      return toolMessage
        ? mapToolMessageToAction(toolMessage, messages)
        : mapToolCallToAction(toolCall);
    });
    return <ActionStep actions={actions} reasoningText={reasoningText} />;
  }

  return (
    <div className={styles.aiRow}>
      <div className={styles.aiBubble}>
        {reasoningText ? <p className={styles.text}>{reasoningText}</p> : null}
      </div>
    </div>
  );
}

Rendering Pipeline

Each message flows through MessageView exactly like Open SWE's AssistantMessage:

Message typeRendered asNotes
human HumanMessageView Right-aligned bubble (unchanged behavior).
ai + tool calls ActionStep Collapsible reasoning block + one ActionItem per tool call.
ai (no tool calls) plain AI bubble Final assistant text.
tool (consumed) null Already shown inside its owning AI action step.
tool (orphan) ActionItem Standalone result fallback.
stream.messages (ordered) │ ▼ MessageView │ ├─ human ───────────────────────────▶ right-aligned bubble │ ├─ tool ──▶ owned by an AI tool_call? ── yes ──▶ null (rendered inline) │ │ │ └── no ──▶ standalone ActionItem │ └─ ai ──▶ tool_calls? ── no ──▶ final text bubble │ └── yes ──▶ ActionStep ├─ reasoning (collapsible) └─ ActionItem per tool call ├─ status: generating → done (success/error) └─ output (collapsible <pre>)

Status is derived from the joined ToolMessage:

  • generating — tool call streamed, result not yet received.
  • done / success — result received with status !== "error".

Key Takeaways

  • The renderer inherits Open SWE's logic (type guards → extract tool calls → join on tool_call_id → dispatch), not its component styling.
  • Nixx's state now carries messages (display) and internalMessages (LLM context), keeping the transcript intact while leaving room to trim context later.
  • Tool messages now carry name and status, so the frontend can render tool identity and success/error without string-sniffing.
  • Adding "messages" to the stream mode enables token-level AI streaming, matching Open SWE's live-update feel.
  • No new frontend dependencies were added — everything uses Nixx's existing CSS modules and CSS variables.
