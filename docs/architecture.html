Overview

Nixx runs a coding agent that executes work inside an isolated sandbox. The agent does not touch the filesystem or shell directly. Instead it communicates with the sandbox through two BullMQ queues backed by Redis.

┌─────────────────────┐ Queue A ┌──────────────────────┐ │ agent-brain │ agent-to-sandbox │ sandbox-worker │ │ (LangGraph + HTTP) │ ───────────────────────▶│ (executor process) │ │ │ │ │ │ SandboxClient │ ◀───────────────────────│ executes commands │ │ (await result) │ sandbox-to-agent │ returns output │ └─────────────────────┘ Queue B └──────────────────────┘ ▲ │ HTTP POST /run │ ┌─────────────────────┐ │ web │ │ (Next.js backend) │ │ auth + thread mgmt │ └─────────────────────┘

The split is deliberate:

  • agent-brain owns reasoning (LangGraph) but is sandbox-agnostic.
  • sandbox-worker owns execution but is agent-agnostic.
  • The only contract is the message shapes and queue names in @repo/contracts.

Message Contract

SandboxCommandMessage Queue A

{
  type: "command",
  commandId: string,       // correlation id
  threadId: string,
  conversationId: string,
  sandboxId: string,
  command: SandboxCommandName,
  args: Record<string, unknown>,
}

SandboxResultMessage Queue B

{
  type: "result",
  commandId: string,       // same id as the request
  threadId: string,
  conversationId: string,
  sandboxId: string,
  output: string,
  exitCode: number,
  error?: string,
}

commandId is generated by the agent's SandboxClient using randomUUID(). The agent stores a pending resolver keyed by that id.

Supported Sandbox Commands

The sandbox worker supports read, search, shell execution, and file mutation inside the cloned repository.

Sandbox Client

Defined in apps/agent-brain/src/bullmq-sandbox-client.ts.

class BullMqSandboxClient implements SandboxClient {
  async call(input) {
    const commandId = randomUUID();
    await agentToSandboxQueue.add("command", { type: "command", commandId, ...input });
    return new Promise((resolve, reject) => {
      // resolved by result-consumer when the matching result arrives
    });
  }
}

There is a hard timeout of 120_000ms.

Result Consumer

Defined in apps/agent-brain/src/result-consumer.ts.

It runs a BullMQ Worker on sandbox-to-agent. For each result job, it looks up the matching pending call by commandId and resolves it.

Agent Graph

Defined in packages/agent/programmer/graph.ts.

createProgrammerGraph({
  sandboxClient,
  threadId,
  conversationId,
  sandboxId,
});
NodeRole
generate-actionBinds sandbox tools and produces the next action
take-actionExecutes the first tool call from the last AI message
reasoning-thinkingPlaceholder loop node
end-conclusionSummarizes the completed run

Routing:

  • mark_task_complete → end-conclusion
  • any other tool call → take-action
  • plain text response → end-conclusion
  • after take-action → back to generate-action

Sandbox Worker

Defined in apps/sandbox-worker/src/main.ts.

It runs a BullMQ Worker on agent-to-sandbox, executes the command, then publishes a SandboxResultMessage to sandbox-to-agent.

Running the System

# install
bun install

# start Redis, then run these in separate terminals:

# 1. sandbox worker
bun run dev --filter=sandbox-worker

# 2. agent brain
bun run dev --filter=agent-brain

# 3. web (primary backend)
bun run dev --filter=web

What is Deferred

  • Sandbox modify tools (write_file, edit)
  • Checkpointer (graph state persistence)
  • SSE / streaming agent events
  • UI for agent output
  • GitHub installation token wiring in the agent path
  • Real sandbox provisioning (currently sandboxId falls back to threadId)

Typechecking

bun run check-types
